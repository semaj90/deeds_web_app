# Legal Taxonomy Clustering System - Requirements Document

## Introduction

The Legal Taxonomy Clustering System automatically discovers and organizes legal statutes into meaningful categories using machine learning. It uses Self-Organizing Maps (SOM) to discover emergent patterns in statute embeddings, then applies K-Means clustering to assign crisp labels. This creates a dynamic, data-driven taxonomy that helps users navigate and understand relationships between different areas of law.

## Glossary

- **Self-Organizing Map (SOM)**: An unsupervised neural network that discovers emergent patterns in high-dimensional data by mapping embeddings to a 2D grid
- **K-Means Clustering**: An unsupervised algorithm that partitions data into K clusters by minimizing within-cluster variance
- **Statute Embedding**: A 768-dimensional vector representation of a statute generated by the Gemma3 embedding model
- **Cluster Label**: A human-readable category name assigned to a cluster (e.g., "Violent Crimes", "Property Crimes")
- **Cluster Confidence**: A score (0-1) indicating how well a statute fits its assigned cluster
- **Echo Cache**: A Redis-based cache tracking search hit frequency for popular queries
- **RabbitMQ Job Queue**: A message queue for asynchronous clustering jobs with retry logic
- **XState Machine**: A state machine orchestrator for managing clustering workflow transitions
- **Qdrant Payload**: Metadata stored alongside vectors in Qdrant (e.g., cluster IDs, labels)
- **Change Detection**: Monitoring for significant label changes (>20%) between clustering runs
- **Operator Alert**: A notification to human operators when significant changes are detected

## Requirements

### Requirement 1: Clustering Job Queue

**User Story:** As a system administrator, I want clustering jobs to be queued and processed asynchronously, so that the system can handle large datasets without blocking user requests.

#### Acceptance Criteria

1. WHEN a new statute is indexed, THE system SHALL publish a NEW_DATA event to RabbitMQ queue `clustering.jobs`
2. WHILE clustering jobs are pending, THE system SHALL retry failed jobs up to 3 times with exponential backoff (1s, 2s, 4s)
3. IF a clustering job exceeds 1 hour execution time, THEN THE system SHALL timeout and mark the job as failed
4. WHERE clustering is disabled, THE system SHALL skip job publishing and log a debug message
5. THE system SHALL track job status (pending, processing, completed, failed) in Redis with 24-hour TTL

### Requirement 2: XState Clustering Orchestration

**User Story:** As a system architect, I want clustering workflows to be orchestrated with state machines, so that complex transitions are managed reliably with rollback capability.

#### Acceptance Criteria

1. WHEN a clustering job starts, THE system SHALL transition through states: waiting → queue → clustering → tagging → indexing → complete
2. WHILE in any state, THE system SHALL retry up to 3 times before transitioning to error state
3. IF a state transition fails, THEN THE system SHALL rollback to the previous state and emit an error event
4. WHERE version tracking is enabled, THE system SHALL store cluster version before and after each run
5. THE system SHALL emit events for job completion, state transitions, and errors for monitoring

### Requirement 3: SOM Clustering Algorithm

**User Story:** As a data scientist, I want to use Self-Organizing Maps to discover emergent patterns in statute embeddings, so that natural legal categories emerge from the data.

#### Acceptance Criteria

1. WHEN clustering begins, THE system SHALL initialize a 10x10 SOM grid on statute embeddings (768-dim → 2D)
2. WHILE training the SOM, THE system SHALL use 100 epochs with learning rate decay from 0.5 to 0.01
3. IF a statute embedding is missing, THEN THE system SHALL skip it and log a warning
4. WHERE SOM training completes, THE system SHALL compute cluster centroids from grid neurons
5. THE system SHALL store SOM grid state and centroids in Redis for later K-Means application

### Requirement 4: K-Means Labeling

**User Story:** As a legal domain expert, I want K-Means clustering to assign crisp labels to statute groups, so that each statute has a clear category assignment.

#### Acceptance Criteria

1. WHEN K-Means runs, THE system SHALL cluster SOM centroids into K=8 clusters (configurable)
2. WHILE assigning statutes to clusters, THE system SHALL compute confidence scores (0-1) based on distance to cluster center
3. IF confidence is below 0.7, THEN THE system SHALL flag the statute for manual review
4. WHERE cluster labels are generated, THE system SHALL use LLM to suggest labels based on statute content
5. THE system SHALL store cluster assignments in Qdrant payloads: `som_cluster_id`, `kmeans_label`, `cluster_confidence`

### Requirement 5: Change Detection and Alerts

**User Story:** As an operator, I want to be notified when clustering results change significantly, so that I can review and validate new categories.

#### Acceptance Criteria

1. WHEN a new clustering run completes, THE system SHALL compare labels to previous run
2. WHILE comparing, THE system SHALL calculate percentage of statutes with changed labels
3. IF label changes exceed 20%, THEN THE system SHALL emit an operator alert with change summary
4. WHERE change detection is enabled, THE system SHALL store change history in PostgreSQL for audit trail
5. THE system SHALL include affected statute counts and confidence metrics in alert payload

### Requirement 6: Echo Ranking Integration

**User Story:** As a user, I want search results to be boosted by popularity, so that frequently accessed statutes rank higher.

#### Acceptance Criteria

1. WHEN a statute is searched, THE system SHALL increment its hit counter in Redis echo cache
2. WHILE ranking results, THE system SHALL apply boost: `semantic_score + echo_hits * 0.15`
3. IF echo cache expires (24-hour TTL), THEN THE system SHALL reset hit counters
4. WHERE echo ranking is enabled, THE system SHALL include hit counts in search response metadata
5. THE system SHALL track echo hits per statute per day for analytics

### Requirement 7: Cluster Filtering in Search

**User Story:** As a user, I want to filter search results by cluster category, so that I can narrow results to specific legal domains.

#### Acceptance Criteria

1. WHEN a user selects a cluster filter, THE system SHALL query Qdrant with `som_cluster_id` or `kmeans_label` filter
2. WHILE filtering, THE system SHALL return only statutes matching the selected cluster
3. IF multiple clusters are selected, THEN THE system SHALL return statutes in any of the selected clusters (OR logic)
4. WHERE cluster metadata is available, THE system SHALL display cluster name and confidence in results
5. THE system SHALL cache cluster filter options for 1 hour to improve performance

### Requirement 8: Clustering Monitoring and Metrics

**User Story:** As a system operator, I want to monitor clustering performance and health, so that I can detect and resolve issues quickly.

#### Acceptance Criteria

1. WHEN clustering completes, THE system SHALL record metrics: execution time, statute count, cluster count, average confidence
2. WHILE monitoring, THE system SHALL track job success rate and average retry count
3. IF any metric exceeds thresholds, THEN THE system SHALL emit a warning to monitoring system
4. WHERE metrics are collected, THE system SHALL store them in time-series database for historical analysis
5. THE system SHALL expose metrics via `/api/health/clustering` endpoint for health checks

## Summary

This requirements document defines a comprehensive clustering system that:
- Queues and processes clustering jobs asynchronously with reliability
- Orchestrates complex workflows using state machines with rollback capability
- Discovers emergent patterns using Self-Organizing Maps
- Assigns crisp labels using K-Means clustering
- Detects and alerts on significant changes
- Integrates with search ranking and filtering
- Provides comprehensive monitoring and metrics

All requirements follow EARS patterns and INCOSE quality rules for clarity, measurability, and traceability.
