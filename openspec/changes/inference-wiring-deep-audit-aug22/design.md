## Context

This change is the write-up of a live-code deep audit (2026-08-22), run via 6 parallel research forks against `sveltekit-frontend/src/lib/server/ollama.ts`, `ai/openai-facade.ts`, `ai/mcp-tool-bridge.ts`, `ai/bifrost-provider.ts`, `scripts/launch-turboquant.ps1`, `redis.ts`/`cache-keys.ts`, `trace-mcp-server.ts`, and the retrieval/router files. It cross-checked every claim in root `CLAUDE.md` against the actual running code rather than trusting the docs. Three findings were bugs with an unambiguous correct fix (applied immediately); six more were recorded for follow-up. A second same-day pass then acted on four of those six: two doc-drift corrections, the miniforge ACP registration, and the `trace-mcp-server.ts` Redis consolidation. Two follow-ups remain genuinely open (see Open Questions).

- Record every other finding with enough evidence that a future session (or the operator) can decide what to do without re-running the audit.

## Decisions

1. **Streaming fix implemented as a shared helper, not three copy-pasted blocks.** `fetchStreamedChatCompletion()` in `ollama.ts` centralizes SSE parsing + content/tool_call delta assembly for the TurboQuant and llama-server-fallback call sites. The Bifrost gateway call site needed its own inline copy (not the shared helper) because it also has to recover `extra_fields.cache_debug` from the stream, which the generic helper's return shape doesn't carry — duplicating ~40 lines was judged preferable to widening the shared helper's contract for one caller's side channel. Considered reusing the pre-existing `streamText()` generator in `config/llama-server.ts`, but that helper only yields content chunks (no tool_call delta assembly) and would have needed a rewrite anyway — flagging that `config/llama-server.ts`'s own `generateText()` *also* still uses `stream: false` and was left unfixed as out of scope (not on the `bifrostChat()` call path this audit was scoped to).

2. **Raw-mode fix removes the branch rather than repairing its condition.** The original code had `const selectedLane = 'bifrost'` immediately followed by `if (selectedLane === 'bifrost') { runLdrChat(...) }` — the constant and the branch target were simply mismatched (likely a copy-paste from a different lane-selection block). Rather than reconstruct the original author's intent, this fix makes the code match its own inline comment and CLAUDE.md's documented intent: TurboQuant first, Bifrost fallback, no LDR in raw mode.

3. **Allowlist fix corrects names in place rather than removing the stale tools.** Both `kag.multi_lane_search`/`kb.search_summary_tree` are live superset/renamed equivalents of the intended tools (confirmed via direct grep against `trace-mcp-server.ts` registration call sites), so correcting the string is safe and preserves the allowlist's original intent.

4. **Dead files archived via the documented `deeds_labs/archive/` + `docs/archive-manifest.json` pattern**, not the alternative git-tag cold-archive pattern also described in CLAUDE.md — simpler, already-precedented for small isolated dead-code removals, and `git rm` after archiving still leaves full recovery via git history in addition to the archive copy.

5. **Doc-drift fixed via an explicit STALE banner + inline correction, not silent rewrite.** Both root `CLAUDE.md` sections (the June 2026 "OpenCode + llama-server Config" section and the turbo-probe throw claim inside the Aug 4 2026 frozen contract) were edited in place with a dated correction note and a cross-reference to this change, rather than deleting the old text — preserves the historical record while making the current-truth flags unambiguous for the next reader.

6. **Miniforge sidecar registered as a second discovery surface, not a new client.** `ACPToolRegistry.ts`'s new `miniforge:health`/`analyze`/`extract` handlers import the exact same `createMiniforgeNlpSidecarClient()` shared module `trace-mcp-server.ts` already uses (`$lib/server/nlp/miniforge-nlp-sidecar.js`) — zero new HTTP client code, purely additive tool discoverability via `GET /api/acp/tools`. This directly closes the gap root CLAUDE.md's "Duplication Prevention" section flagged on 2026-08-09 ("a live Docker NLP sidecar with zero ACP registrations").

7. **Redis consolidation: extended `makeRedis()` rather than forcing every site to the exact original default config.** Two variants of duplicate boilerplate were found: 9 sites nearly byte-identical to `makeRedis()`'s original options, and 6 sites using a different shape (`connectTimeout: 3000, enableReadyCheck: false`, **missing the error-listener attachment entirely** — a real crash-risk gap, since Node's default behavior for an unhandled EventEmitter `'error'` event is to throw). Rather than force all 15 sites onto identical timeouts, `makeRedis()` gained optional `{connectTimeoutMs, commandTimeoutMs}` parameters so each site keeps its original timeout behavior while gaining the safety hardening (error listener, `retryStrategy: () => null`, `enableOfflineQueue: false`, `enableReadyCheck: false`) uniformly. One site's `commandTimeout: 4000` was verified as a real, ioredis-supported option (checked `node_modules/ioredis/built/*.d.ts` directly) before deciding to preserve it rather than assume it was dead/mistaken configuration. Two more sites were found mid-task already calling `makeRedis()` correctly but with a leftover dead `Redis` import above them — removed as a drive-by cleanup since they were directly adjacent to the work already in progress.

## Risks / Trade-offs

- **[Risk] Downstream callers of `bifrostChat()` may have relied on synchronous, single-shot fetch timing → [Mitigation]** The public contract (`Promise<string>` or `Promise<{content, tool_calls, sessionId}>`) is unchanged; only the internal wire protocol changed. Verified via `tsc --noEmit` — zero new errors.
- **[Risk] `raw: true` callers built around the old (buggy) LDR-routed behavior will see a behavior regression, not just a bugfix →** **Mitigation**: none applied; flagged as the one plausible caller-visible regression. Search `req.raw` call sites if unexpected behavior is reported.
- **[Risk] Correcting `kag.search`→`kag.multi_lane_search` changes the tool's actual capability surface (superset, not a pure rename) →** **Mitigation**: acceptable; previously-broken callers now work and get a superset of intended data.
- **[Risk] The `trace-mcp-server.ts` Redis consolidation touches 15 call sites in a live, long-running MCP server process that every downstream tool depends on — a mistake there breaks everything at once, not just one feature →** **Mitigation**: every replacement preserved each site's exact subsequent `.connect()`/`.quit()` control flow (only the construction boilerplate was replaced); `tsc --noEmit` confirmed zero new errors across the whole file; the two structurally-different sites (`commandTimeout`, host/port-form construction) were read individually and verified against ioredis's actual type definitions rather than assumed equivalent. **Live-verified 2026-08-22** (task 6 in tasks.md): restarted the process, exercised 4 touched tools — 3 clean passes (`kag.recall_similar_fix`, `kag.multi_lane_search`, `LLMS.md.context_for_file`), 1 reached-and-passed-through the Redis layer but failed later at an unrelated pre-existing Postgres `ON CONFLICT` schema bug in `fixer-memory.ts` (recorded as its own out-of-scope finding, not a Redis regression — the Redis client construction/connect succeeded, confirmed by the call reaching the Postgres statement at all).
- **[Trade-off] The 19 SHOULD_CONSOLIDATE direct-`:8090` callers and the ACE-reranker wiring question remain open.** Explicitly accepted per this repo's own governance model: "inventory first, remediate later, as its own explicit task." Both now have enough recorded evidence (classification table for the former, scoring-spine description for the latter) that a future session doesn't need to re-derive them.

(Needs retrieval-quality evaluation, not a code-only decision.) **Investigated further 2026-08-22, found new material information that changes the shape of this question — still not implemented.** The final ranked-candidate assembly point was located precisely: `assembleACEContext()` (the real 7678-line implementation in `features/ai/ace/context-assembler.ts`, not the thin re-exporting wrapper of the same name in `ace/context-assembler.ts`) builds `finalContext.acePayloads` via `selectAcePayloads()` then sorts it by `_aceRouting.score` at line ~3385 — that sort is the correct insertion point for a second-pass rerank, option (b) from the original 3-option list. But: **`context-assembler.ts` already calls the raw cross-encoder engine directly** — `rerankWithCrossEncoder()` (from `cross-encoder-reranker.ts`, the same engine `canonical-rerank-executor.ts`'s `MixedbreadCanonicalReranker` wraps) is called inside `fetchCodebaseContext()` (line ~6820), which `assembleACEContext()` itself calls twice (lines ~1952, ~2206) to populate `codebaseContext`/part of what feeds `acePayloads`. So the original framing — "the canonical reranker is never wired into ACE" — was correct about the *canonical wrapper* (caching, provenance, dual-identity, 16-point rejection reasons) but incomplete: the underlying cross-encoder model is already live in part of the pipeline, uncached and unwrapped. Inserting `rerankCanonicalFeatureEnvelopes()` as a blanket second pass over the final merged `acePayloads` risks double-reranking content that already went through raw cross-encoder scoring once, with unknown interaction effects (does a second cross-encoder pass on already-cross-encoder-ranked content improve or just add latency/noise?) and no eval data to judge either way. Also verified: `MixedbreadCanonicalReranker.rerank()`'s underlying `rerankWithCrossEncoder()` call chain has **up to 20s per-backend timeouts** in its fallback chain (`cross-encoder-reranker.ts`, multiple `AbortSignal.timeout(20_000)` sites) — a real production latency risk if wired unconditionally into the hot path every ACE-assembled chat/RAG response goes through. **Not implemented.** If this is picked up: (a) first determine whether `fetchCodebaseContext`'s existing cross-encoder call should be the *only* rerank pass (i.e. route it through the canonical wrapper for caching/provenance instead of adding a second pass elsewhere), or whether a genuinely separate second pass over the merged multi-source list (kb+case+rag chunks, not just codebase context) is wanted; (b) any live-wiring must have a hard timeout independent of the reranker's own internal chain (`Promise.race` against a short deadline, e.g. 2-4s) and a non-fatal fallback to the existing `_aceRouting.score` order on any failure/timeout; (c) should ship env-gated and default-off (e.g. `ACE_CANONICAL_RERANK_ENABLED=false`) until eval data justifies flipping it on for all production traffic — this is not a decision to make via default under auto-mode.
