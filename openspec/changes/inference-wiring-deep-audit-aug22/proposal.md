## Why

A user-requested deep audit (2026-08-22) of the `hforf.gguf` / llama-server `:8090` / OpenAI facade / Bifrost / ACE / Redis-Valkey / TRACE MCP wiring — verified against live code, not documentation — found three real correctness bugs, four dead duplicate files, and six additional findings (architecture gaps, undocumented debt, and doc drift) that need a decision or a follow-up change rather than a blind fix. This proposal records what was fixed, what was archived, and what remains open, per this repo's own "Duplication Prevention" and "Agent Execution Integrity" hard rules — findings must be recorded even when not immediately acted on.

## What Changes

- **Fixed**: `bifrostChat()` (`sveltekit-frontend/src/lib/server/ollama.ts`) sent `stream: false` at all three inference call sites (TurboQuant, llama-server fallback, Bifrost gateway), contradicting the documented Gemma4 rule that thinking-token budgets can exhaust `max_tokens` before any content token appears unless streamed. Added a shared `fetchStreamedChatCompletion()` helper and an inline SSE assembler for the Bifrost gateway path; all three now stream and assemble content + tool_call deltas correctly.
- **Fixed**: `openai-facade.ts`'s `raw: true` passthrough mode had `selectedLane` hardcoded to the literal `'bifrost'`, which the `if` branch mapped to `runLdrChat()` (a 120s-capable research/poll pipeline) instead of the documented fast TurboQuant→Bifrost direct-model path. The TurboQuant/Bifrost branches were unreachable dead code. Removed the mislabeled branch; raw mode now genuinely tries TurboQuant first, falls back to `bifrostChat()`.
- **Fixed**: `TRACE_TOOL_ALLOWLIST` (`mcp-tool-bridge.ts`) had 2 of 12 entries referencing tool names not registered on `trace-mcp-server.ts` (`kag.search` → should be `kag.multi_lane_search`; `knowledge.search_summary_tree` → should be `kb.search_summary_tree`). Either would silently fail if a model tried to call them. Corrected both.
- **Archived** (not deleted — per repo convention): 3 dead duplicate Ollama/llama-server client files with zero production callers (`src/lib/server/llm/ollama-client.ts`, `src/lib/server/utils/ollama-client.ts`, `src/lib/server/llm/ollamaClient.ts`) plus the latter's now-orphaned test. Copies + SHA-256 hashes recorded in `docs/archive-manifest.json`, bytes preserved at `deeds_labs/archive/2026-08-22/dead-ollama-clients/`.
- **Fixed in follow-up pass (same day)**: both root `CLAUDE.md` doc-drift items corrected in place — the "OpenCode + llama-server Config" section's stale `gemma4-opencode.jinja`/`--reasoning-format none` claims (both drift items live in the *same* file, not split across root/sveltekit-frontend as first thought — the June 2026 section simply predates and was never reconciled against the Aug 4 2026 frozen contract earlier in the same file), and the turbo-probe "hard throw" overstatement (actually warn-and-fallback to q8_0/q8_0).
- **Fixed in second follow-up pass (same day)**: `trace-mcp-server.ts`'s 15 inline `new Redis()` constructions consolidated onto its own `makeRedis()` factory (extended to support per-call `connectTimeoutMs`/`commandTimeoutMs`) — 6 of those 15 were missing an error-listener attachment entirely, a real crash-risk gap now fixed uniformly, not just a style cleanup. Also registered the miniforge NLP sidecar in `ACPToolRegistry.ts` (`miniforge:health`/`analyze`/`extract`, reusing the same shared client `trace-mcp-server.ts` already imports) so it's discoverable via `GET /api/acp/tools`, closing the gap root CLAUDE.md's "Duplication Prevention" section flagged back on 2026-08-09.
- **Classified, then partially consolidated** (see design.md + tasks.md §5.6b): the 111+ direct-`:8090` callers were narrowed to 37 real candidates and classified — 19 SHOULD_CONSOLIDATE, 6 JUSTIFIED_LOW_LEVEL, 2 JUSTIFIED_ISOLATED_BENCHMARK, 10 UNCLEAR. 3 of the 19 fully converted to `bifrostChat()` (2 of those were blocked on missing `BifrostChatOptions` fields, resolved same session — see next item), 1 partially (model literal only), 15 remain — real behavior-changing work across many files, honestly left incomplete rather than rushed.
- **Fixed a real API gap this sweep surfaced**: extended `BifrostChatOptions` (`ollama.ts`) with `topP`/`topK`/`responseFormat` passthrough — this was blocking 4 identified files (`gemma4-intent-engine.ts`, `legal-skills.tool.ts`, `admin/subagent-orchestrator.ts`, `analysis/holistic-synthesizer.ts`) from safely adopting `bifrostChat()`. Unblocked and converted the first 2; the latter 2 need their own careful per-call-site read (each has 2 call sites) not completed this session.
- **Assessed, not implemented** (needs operator input): whether/how to wire `canonical-rerank-executor.ts` into ACE's retrieval path. Confirmed the reranker is real with 6+ live callers via its standalone route; recorded 3 concrete integration options with their tradeoffs in design.md rather than picking one without eval data.
- **Fixed in third follow-up pass (same day, user-directed)**: 8 files (`analysis/summarizer.ts` plus 7 more found via a dedicated scoping sweep) converted from hardcoded model-name string literals to live resolution via `getLlamaSessionDescriptor()` (`GET /v1/models`, cached), so requests track what `:8090` actually has loaded instead of trusting static env-derived config. `summarizer.ts` was additionally converted from a hand-rolled direct-fetch SSE client to `bifrostChat()`. Two related files were found and left unconverted because `bifrostChat()`'s options interface doesn't support the sampling/format parameters they need (`top_p`/`top_k`, `response_format: json_object`) — a real API-surface gap this sweep surfaced. Three more files were flagged (not investigated) as a possible separate Ollama-vs-llama-server boundary-rule question.

## Post-proposal updates (2026-08-22, same day)

Everything above reflects the state when this proposal was first written. Two substantial follow-on passes happened the same day:

- **The `:8090`-consolidation sweep (task 5.6, item 13 above) is now fully complete** — all 19 SHOULD_CONSOLIDATE files converted, not just the first few. In the process, **9 more real `stream:false` Gemma4 thinking-block-risk bugs were found and fixed**, none among the original 3 sites finding #1 covered (see tasks.md 5.6d–5.6g for the full per-file list).
- **`BifrostChatOptions` was extended a second time**, adding `includeMetadata: true` (opt-in — the default string-returning behavior is 100% unchanged) which resolves to real token usage read from llama-server's own response (verified live against `:8090`, not estimated) and an honest, literal backend identity (`'cache-l1' | 'cache-l2' | 'turboquant' | 'llama-server' | 'bifrost-gateway'`, never fabricated on a cache hit). This unblocked the 4 remaining consolidation targets (`admin/subagent-orchestrator.ts`, `ff1/agent/gemma4-repair-planner.ts`, `analysis/holistic-synthesizer.ts`, `graph/community-graph.ts`), all now converted.
- **The ACE canonical-rerank question is implemented, not just recorded** — as option (b) (second pass over the blend's top-K), env-gated and **OFF by default** (`ACE_CANONICAL_RERANK_ENABLED` unset ⇒ no-op passthrough), with its own independent hard timeout (`Promise.race`, default 3s) separate from the reranker's internal fallback chain (which has per-backend timeouts up to 20s), and a non-fatal fallback to the pre-existing order on any failure. This was implemented only after discovering that `context-assembler.ts` already calls the underlying cross-encoder engine directly elsewhere in the pipeline (`fetchCodebaseContext()`), a fact that materially changes what "wire in the reranker" means and that wasn't known when this proposal was first written — see design.md Open Question 2 for the full account. **Whether to actually enable it in any environment is still an open, eval-informed operator decision**; this proposal only makes that decision safely testable without forcing a production behavior change.
