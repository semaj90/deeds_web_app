### 13a. Scene generation design gaps and proposed pipeline (2026-11-16, planned, all OPEN)

Evidence basis (live, read-only): sample video `0f067235-4957-4783-82a5-ad93bd71daab` is 614.8 s long; transcript spans 0–619.8 s in 90 segments; 61 scene cuts; the probe reports `fps: 0` for AV1 (data gap, SCENE-26). A 20 s clip is 3.3% of the source, so a clip must be chosen by cue density, not taken from the start.

- [x] SCENE-DEC-A DECIDED 2026-11-16 by the operator: clip length **20 s**. Options considered: options 8 s, 20 s, 30 s. Recommendation: make `clipSeconds` a versioned manifest parameter with default **20 s**. Eight seconds cannot carry who/what/why/how with a witness-level explanation; 30 s costs more render and review time for the first build. SCENE-17 hard-codes 20 s; a different length needs a new schema version.
- [x] SCENE-DEC-B DECIDED 2026-11-16 by the operator: **2D storyboard** (option 1). Options considered: (1) 2D storyboard of stills with captions, (2) rendered 2D frames or MP4 from the 3D scene, or (3) interactive 3D only. Recommendation: storyboard first (1), because it needs no renderer proof and states the demonstrative limits on every panel; (2) follows only after SCENE-24 passes.
- [ ] SCENE-16 Beat extraction (who/what/why/how): derive beats from the authorized timeline (`timeline-reconstruction-bridge.ts`, which already maps events to `ScenePrompt`), transcript segments (by segment ID and timestamp), and summaries. Every beat must cite evidence IDs and `sourceRevision`. Summaries are derived features, not canonical facts (section 16 caveat); a beat that cites only a summary is marked HYPOTHESIS. The LLM proposes beats via the existing synthesis route; a validator rejects any uncited beat. Keep raw model output and rejected beats for audit.
- [ ] SCENE-17 PARTIAL (2026-11-16): schema, validator and canonical SHA-256 implemented in `sveltekit-frontend/src/lib/server/scene/scene-intent-v1.ts`; 11 spec tests pass (`scene-intent-v1.spec.ts`), covering uncited beats, measured-vs-timeline rule, 20 s clip limit, duplicate ids, and key-order-independent hash. NOT PROVEN: planner (LLM) emission through the synthesis route, and any evidence-revision readback. Original item text: `SceneIntent` schema (Zod, versioned): `schemaVersion`, `clipSeconds`, `seed`, `beats[]` (text, citations, `kind: measured|hypothesis|fixture`), `actors[]`, `props[]`, `cameraKeyframes[]`, `evidenceAnchors[]`. The model may emit only this shape. Same input and seed must yield the same JSON bytes (canonical serialization + SHA-256).
- [ ] SCENE-18 PARTIAL (2026-11-16): deterministic selector implemented in `sveltekit-frontend/src/lib/server/scene/clip-window-v1.ts` (policy `atlas.scene-clip-window.v1`, weights: 1 per transcript word, 5 per scene cut, earliest-start tie-break). On the real captured fixture `fixtures/sample-video-0f067235.clip-window.json` (live API read, duration 614.781 s) the 20 s window is **574–594 s**: 70 words, 2 scene cuts, repeatable; the transcript there is a coherent passage on font subsetting. 7 spec tests pass. NOT PROVEN: the token-budget check against the selected VLM (the 8,000-token finding above) and the frame-dedupe input. Original item text: Deterministic clip window: score candidate windows of `clipSeconds` by transcript cue density, scene-cut timestamps (`sceneDetection`), and frame dedupe (dHash from section 16). Ties resolve by earliest start. Test: 0-frame, exact-fit, overflow, and corrupt-timestamp cases. The frame budget must be checked against the token budget: section 16 found 58 × 140 frames ≈ 8,120 tokens, which exceeds an 8,000-token budget.
- [ ] SCENE-19 Camera track as data (the "camera buffer"): a camera track is a precomputed list of keyframes `{t, position, lookAt, fov}` per beat in the manifest; the renderer only interpolates them. No model or runtime code chooses camera moves. Sample at a fixed frame rate (for example 30 fps; 20 s = 600 frames). The FFT and similarity tools are not camera tools. This is not an FFT-to-scene step.
- [ ] SCENE-20 Primitive vocabulary and composition: use the existing `scene-primitive-registry-v1.ts` (box, sphere, cylinder, cone, torus, rectangle, circle, plus the polygon-prism parts used by the sword assembly). Define a courtroom kit (bench, witness stand, table, door, and a labelled person proxy) as registry entries with `dimensionsMeters` and collider. Composition is a parent/child tree with positions in meters; no ad-hoc meshes. Animation clips need a registry, which does not exist yet (Mixamo-style clips are proposed, not verified). Each kit entry needs a measured or documented real-world size before it is used as evidence.
- [ ] SCENE-21 Evidence placement: markers and drag-and-drop evidence cards (SCENE-07, SCENE-11) create `evidenceAnchors`. An anchor is `measured` only when its source is a calibrated measurement (SCENE-12); otherwise it is `hypothesis`. Placement is never derived from FFT, cosine similarity, Hilbert transforms, PageRank, or top-k ranking, which belong to retrieval and ranking owners. The term "Hilbert/jspace primitive" has no definition in this repo; it needs one before it is considered.
- [ ] SCENE-22 Zone clustering (optional, tensor work): k-means or SOM over evidence embeddings may group evidence into scene zones. CPU reference first; GPU only through the existing executors, under the VRAM rule (`:8090` holds about 6.2–6.7 GiB, so GPU jobs stay under about 1 GiB and use the human-run release task). Output is a proposal with evidence IDs; it cannot place geometry on its own.
- [ ] SCENE-23 Voronoi destructible props (UNASSIGNED challenger): no code exists in the repo. A fracture of a prop (for example broken glass in a hypothesis event) is only a visual aid. It needs a concrete use case, mesh provenance, and a HYPOTHESIS label. Do not start it before SCENE-20 passes.
- [ ] SCENE-24 Render path: the runtime mesh format is GLB (SCENE-09). Define UV sets per material, a linear working color space with a fixed tone-mapping choice, and a fixed anti-aliasing setting. Renderer target is Babylon.js for the courtroom simulation, following the proposed renderer-ownership split in the project CLAUDE.md (marked proposed, not yet operator-approved); confirm before building against it. Test: the same SceneIntent and seed give the same frame hashes under SwiftShader in CI; the GPU path is checked separately.
- [ ] SCENE-25 Output and chain of custody: each storyboard panel or frame records the source revisions, SceneIntent hash, render settings, and a visible label "Demonstrative reconstruction — not original footage" with the beat's confidence and HYPOTHESIS/measured status. Upscaled or DLSS frames are excluded from exports (SCENE-15).

### Packing contract (fixed in this section, versioned as v1)
- Header, 120 bytes, little-endian: magic `PIDX` (4), version u16 = 1 (2), reserved u16 = 0 (2), width u32 (4), height u32 (4), paletteCount u16 = 16 (2), pixelFormat u8 = 1 meaning 4bpp (1), nibbleOrder u8 = 2 meaning low nibble is the even pixel, matching the existing owner (1), payloadLength u32 (4), palette 16 x RGBA (64), SHA-256 of payload (32).
- Payload: `ceil(width*height/2)` bytes. Odd pixel counts pad the final low nibble with 0.
- Transparency: palette index 0 is transparent (alpha 0). Source pixels with alpha < 128 map to index 0.
- Opaque quantization: take the 15 most frequent opaque colours (ties broken by ascending RGB value). Each pixel maps to the nearest of these by squared RGB distance, ties to the lower index. Deterministic.
