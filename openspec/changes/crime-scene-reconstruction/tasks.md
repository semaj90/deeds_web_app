## 13. Uploaded evidence to "set the scene" to Detective Mode (planned, 2026-11-04)

Planned workflow, not built. Every item stays open until its gate has a receipt. Storage and worker prerequisites are in section 12 (FAIL-07, STORAGE-01f).

- [ ] SCENE-01 Explicit case action: add **Set the scene** to the authorized evidence board. The user selects evidence for the scene; the action is accepted only after case ownership and evidence-to-case membership checks. Opening or uploading evidence alone does not start reconstruction. Evidence retains its original `caseId` and bytes.
- [ ] SCENE-02 Durable job lifecycle: represent each request as an idempotent scene-generation job in canonical PostgreSQL state, linked to its case and selected evidence revisions. Use bounded retries and explicit completed, failed, and source-missing states; RabbitMQ may wake a worker but does not own completion state.
- [ ] SCENE-03 Qualified inputs: verify exact source bucket/key, readback, SHA-256, source revision, admission/rights status, and eligible timeline references before generation. Distinguish measured source photos/frames, generated **HYPOTHESIS** geometry/events, and synthetic **FIXTURE** assets. If Depth Anything V2 Small contributes a depth map, record its checkpoint, source/depth hashes, dimensions, and `relative_monocular` status; do not treat it as metric ground truth. Any Stable Diffusion/ControlNet appearance output remains a separate hypothesis and cannot replace source bytes, depth, or anchors. Only measured sources may ground evidence anchors.
- [ ] SCENE-04 Reconstruction handoff: use the existing reconstruction lane (`timeline-reconstruction-bridge.ts`, `:8092/reconstruct`, or `comfyui.render`) behind a bounded worker; do not run reconstruction in the upload request or introduce an unqualified generator. FLUX/Wan output may be used only as separately versioned **HYPOTHESIS** storyboard/appearance material, never as geometry or evidence authority. Evaluate Wan 3.0 only after its local/API availability, intended-use terms, data handling, and scene-consistency benefits are verified; it is not a replacement geometry lane. Preserve original evidence in `legal-evidence`; write only derived outputs to the configured artifact bucket.
- [ ] SCENE-05 Streamed asset derivation: for a rights-qualified splat admitted to streaming, run pinned SplatTransform steps separately to produce explicit coarse-to-fine LOD inputs and Streamed SOG (`lod-meta.json` plus chunks). Record source hash, tool/version, each asset hash, Gaussian count, and bytes. An optional voxel/collision mesh is a separate derivation with its own parameters and hashes; it is only an interaction proxy for a hypothesis. The synthetic SOG fixture in `parent-atlas-spz-detective-renderer` is format proof, not proof of reconstruction from uploaded evidence.
- [ ] SCENE-06 Artifact and activation gate: register immutable derived assets, case association, source revisions, scene revision, rights/model provenance, manifest, and processing receipt in PostgreSQL; verify exact-object readback and hashes before eligibility. Load only an authorized eligible manifest in Detective Mode, and only through a renderer/loader qualified by `parent-atlas-spz-detective-renderer`. Until then, show queued/progress state and retain the existing depth-relief fallback; do not assume SOG works inside Three.js `WebGPURenderer`.
- [ ] SCENE-07 Evidence interaction and failure behavior: support dragging/placing case evidence cards on scene markers with evidence ID and immutable source revision. Keep measured anchors distinct from positions on inferred geometry and label inferred geometry/timeline actions **HYPOTHESIS**. Missing source, rights rejection, hash mismatch, failed/ineligible generation, or renderer failure must leave the case usable, show a stable reason, and never rewrite original evidence.
- [ ] SCENE-08 Verification: an isolated worker/browser run proves authorized upload → explicit **Set the scene** → durable job/progress/failure → exact artifact readback → eligible manifest → authorized Detective Mode load and LOD selection. Cover cross-case denial, duplicate replay, missing/corrupt assets, fallback, disposal, and no scene job on upload alone. Record independent database and object hashes; an HTTP 201, unit tests, or synthetic conversion alone is insufficient browser proof.
- [ ] SCENE-09 Typed 3D asset loading: qualify the viewer's GLB/glTF mesh path, FBX/OBJ import or normalization path, and SPZ Gaussian-splat path as distinct manifest asset types. Prefer GLB for runtime triangle meshes; use SPZ only for splat data through its qualified loader/renderer. Verify a mixed GLB+SPZ fixture, per-asset provenance/hash, failure fallback, and resource disposal in the browser; do not claim a mesh or splat asset was derived from uploaded evidence unless its source receipt proves that path.
- [ ] SCENE-10 Contextual Detective Mode assistant: add a compact chat composer that expands without replacing the viewer, preserves camera/marker state, and leaves camera controls usable. Load authorized case summaries in parallel with scene/LOD assets with separate progress/failure states. Ground replies and quick suggestion/proposal chips in case evidence references; keep proposals inert until the user explicitly accepts them. An optional NPC/guide is presentation only and must reuse the same case chat contract, not create parallel memory or autonomous scene actions. Cover cross-case denial, citation visibility, chat/scene concurrency, and no mutation on suggestion generation in browser tests.
- [ ] SCENE-11 Anchored marker sizing: show a stable 40–48 CSS-pixel hit target and 24–32 CSS-pixel glyph at every zoom, with a leader line to the projected anchor. Keep source-image pixel/UV annotations distinct from reconstructed-geometry hotspots; bind mesh triangle/barycentric anchors to the exact reconstruction revision and visibly stale or remap them when it changes. Prove pointer placement and anchor persistence in browser tests for both a mesh proxy and the qualified splat path; do not claim splat-surface precision without measured picking accuracy.
- [ ] SCENE-12 Splat calibration receipt (Lane E): an SPZ has no real-world units. Solve a similarity transform (uniform scale, yaw about Y, translation) from measured anchors, such as a doorway of known width, and check it against independent anchors. Store the transform, the splat SHA-256, anchor coordinates, residuals, and tolerance in the manifest. Gate: PASS only when every check residual is within tolerance; an uncalibrated splat carries no metric claims. Current code: `sveltekit-frontend/src/lib/splat/calibration.ts` and `POST /api/splat/calibrate` (stateless; receipts are not yet persisted, so this gate is open). SPZ v4 decoder: `sveltekit-frontend/src/lib/splat/spz-loader.ts` (fzstd 0.1.1 for ZSTD; `spz-loader.test.ts` has 21 tests, including real ZSTD frames from Node 22 `zlib.zstdCompressSync`; 29/29 splat tests pass with calibration). Known limit: fzstd supports back-references up to 2^25 bytes only. The loader now reads each frame's window from its header and rejects anything larger (`SPZ_ZSTD_WINDOW_TOO_LARGE`). SPZ-05 evidence (2026-11-04): two fixtures produced by Niantic's official `ply_to_spz` (nianticlabs/spz commit `11312e4ad836ed06e3da2f3d5b633688d17ebebb`, MIT) in `src/lib/splat/fixtures/`. Degree 0 (5 streams) and degree 1 (6 streams) decode to the official `spz_to_ply` values within 1e-6; the SH layout matches the reference. The official encoder also showed that degree 0 omits the SH stream, which the loader now handles. Degrees 2–4 (3-point fixtures) also match the official decode. Still open: larger files and browser loading (SPZ-08). The repo's `samples/*.spz` are legacy gzip (v1–3), which the loader rejects by design.
- [ ] SCENE-13 Metric marker sizing: after calibration, size markers in meters of the real object, not screen pixels. Screen-constant size applies only to UI handles (SCENE-11). Test: a 0.5 m object's marker measures 0.5 m in the calibrated scene. Current unit proof: `calibration.test.ts` and `measureMarkerWorldDiameterM()` in `three-calibrated-markers.ts`. Browser proof still belongs to SCENE-08/SCENE-11.
- [ ] SCENE-14 Lane C mesh master and FBX checklist: keep a Blender master file as the source of truth. Before any FBX export, record unit scale (1 unit = 1 m), applied transforms, the Y-up/Z-up axis, and a known-length reference measured after import. Record export settings and the output SHA-256. GLB remains the runtime mesh format (SCENE-09).
- [ ] SCENE-15 Enhancement and budget rules: DLSS or other learned upscaling may be used only for interactive performance. Its output must be labeled, and it must be excluded from any exhibit export, because generated detail can look like a recorded fact. Set the per-environment load budget as an operator-chosen project value, not a standard; stream splats and textures in tiles with LOD, following the N64 LOD rendering precedent. That precedent is not a retrieval authority.


### 13a. Scene generation design gaps and proposed pipeline (2026-11-16, planned, all OPEN)

Evidence basis (live, read-only): sample video `0f067235-4957-4783-82a5-ad93bd71daab` is 614.8 s long; transcript spans 0–619.8 s in 90 segments; 61 scene cuts; the probe reports `fps: 0` for AV1 (data gap, SCENE-26). A 20 s clip is 3.3% of the source, so a clip must be chosen by cue density, not taken from the start.

- [x] SCENE-DEC-A DECIDED 2026-11-16 by the operator: clip length **20 s**. Options considered: options 8 s, 20 s, 30 s. Recommendation: make `clipSeconds` a versioned manifest parameter with default **20 s**. Eight seconds cannot carry who/what/why/how with a witness-level explanation; 30 s costs more render and review time for the first build. SCENE-17 hard-codes 20 s; a different length needs a new schema version.
- [x] SCENE-DEC-B DECIDED 2026-11-16 by the operator: **2D storyboard** (option 1). Options considered: (1) 2D storyboard of stills with captions, (2) rendered 2D frames or MP4 from the 3D scene, or (3) interactive 3D only. Recommendation: storyboard first (1), because it needs no renderer proof and states the demonstrative limits on every panel; (2) follows only after SCENE-24 passes.
- [ ] SCENE-16 Beat extraction (who/what/why/how): derive beats from the authorized timeline (`timeline-reconstruction-bridge.ts`, which already maps events to `ScenePrompt`), transcript segments (by segment ID and timestamp), and summaries. Every beat must cite evidence IDs and `sourceRevision`. Summaries are derived features, not canonical facts (section 16 caveat); a beat that cites only a summary is marked HYPOTHESIS. The LLM proposes beats via the existing synthesis route; a validator rejects any uncited beat. Keep raw model output and rejected beats for audit.
- [ ] SCENE-17 PARTIAL (2026-11-16): schema, validator and canonical SHA-256 implemented in `sveltekit-frontend/src/lib/server/scene/scene-intent-v1.ts`; 11 spec tests pass (`scene-intent-v1.spec.ts`), covering uncited beats, measured-vs-timeline rule, 20 s clip limit, duplicate ids, and key-order-independent hash. NOT PROVEN: planner (LLM) emission through the synthesis route, and any evidence-revision readback. Original item text: `SceneIntent` schema (Zod, versioned): `schemaVersion`, `clipSeconds`, `seed`, `beats[]` (text, citations, `kind: measured|hypothesis|fixture`), `actors[]`, `props[]`, `cameraKeyframes[]`, `evidenceAnchors[]`. The model may emit only this shape. Same input and seed must yield the same JSON bytes (canonical serialization + SHA-256).
- [ ] SCENE-18 PARTIAL (2026-11-16): deterministic selector implemented in `sveltekit-frontend/src/lib/server/scene/clip-window-v1.ts` (policy `atlas.scene-clip-window.v1`, weights: 1 per transcript word, 5 per scene cut, earliest-start tie-break). On the real captured fixture `fixtures/sample-video-0f067235.clip-window.json` (live API read, duration 614.781 s) the 20 s window is **574–594 s**: 70 words, 2 scene cuts, repeatable; the transcript there is a coherent passage on font subsetting. 7 spec tests pass. NOT PROVEN: the token-budget check against the selected VLM (the 8,000-token finding above) and the frame-dedupe input. Original item text: Deterministic clip window: score candidate windows of `clipSeconds` by transcript cue density, scene-cut timestamps (`sceneDetection`), and frame dedupe (dHash from section 16). Ties resolve by earliest start. Test: 0-frame, exact-fit, overflow, and corrupt-timestamp cases. The frame budget must be checked against the token budget: section 16 found 58 × 140 frames ≈ 8,120 tokens, which exceeds an 8,000-token budget.
- [ ] SCENE-19 Camera track as data (the "camera buffer"): a camera track is a precomputed list of keyframes `{t, position, lookAt, fov}` per beat in the manifest; the renderer only interpolates them. No model or runtime code chooses camera moves. Sample at a fixed frame rate (for example 30 fps; 20 s = 600 frames). The FFT and similarity tools are not camera tools. This is not an FFT-to-scene step.
- [ ] SCENE-20 Primitive vocabulary and composition: use the existing `scene-primitive-registry-v1.ts` (box, sphere, cylinder, cone, torus, rectangle, circle, plus the polygon-prism parts used by the sword assembly). Define a courtroom kit (bench, witness stand, table, door, and a labelled person proxy) as registry entries with `dimensionsMeters` and collider. Composition is a parent/child tree with positions in meters; no ad-hoc meshes. Animation clips need a registry, which does not exist yet (Mixamo-style clips are proposed, not verified). Each kit entry needs a measured or documented real-world size before it is used as evidence.
- [ ] SCENE-21 Evidence placement: markers and drag-and-drop evidence cards (SCENE-07, SCENE-11) create `evidenceAnchors`. An anchor is `measured` only when its source is a calibrated measurement (SCENE-12); otherwise it is `hypothesis`. Placement is never derived from FFT, cosine similarity, Hilbert transforms, PageRank, or top-k ranking, which belong to retrieval and ranking owners. The term "Hilbert/jspace primitive" has no definition in this repo; it needs one before it is considered.
- [ ] SCENE-22 Zone clustering (optional, tensor work): k-means or SOM over evidence embeddings may group evidence into scene zones. CPU reference first; GPU only through the existing executors, under the VRAM rule (`:8090` holds about 6.2–6.7 GiB, so GPU jobs stay under about 1 GiB and use the human-run release task). Output is a proposal with evidence IDs; it cannot place geometry on its own.
- [ ] SCENE-23 Voronoi destructible props (UNASSIGNED challenger): no code exists in the repo. A fracture of a prop (for example broken glass in a hypothesis event) is only a visual aid. It needs a concrete use case, mesh provenance, and a HYPOTHESIS label. Do not start it before SCENE-20 passes.
- [ ] SCENE-24 Render path: the runtime mesh format is GLB (SCENE-09). Define UV sets per material, a linear working color space with a fixed tone-mapping choice, and a fixed anti-aliasing setting. Renderer target is Babylon.js for the courtroom simulation, following the proposed renderer-ownership split in the project CLAUDE.md (marked proposed, not yet operator-approved); confirm before building against it. Test: the same SceneIntent and seed give the same frame hashes under SwiftShader in CI; the GPU path is checked separately.
- [ ] SCENE-25 Output and chain of custody: each storyboard panel or frame records the source revisions, SceneIntent hash, render settings, and a visible label "Demonstrative reconstruction — not original footage" with the beat's confidence and HYPOTHESIS/measured status. Upscaled or DLSS frames are excluded from exports (SCENE-15).
- [ ] SCENE-26 Data gaps before frame timing: fix the probe so AV1 `fps` is non-zero, or record the frame rate from the decoder; verify the duration (614.8 s) against the container; add a readback test for the video metadata in `videoMetadata`.


### 13b. Video-to-3D reconstruction V1 pilot (2026-11-16, design draft, all OPEN)

Goal: turn one 10 s evidence video (one visible walking person, mostly stationary camera) into a reviewable, source-linked 3D scene: tracked motion, depth, segmentation, a low-poly room blockout, and an animated mannequin placeholder. The first output is an unreviewed proposal, not generated video. Original evidence bytes are never modified.

Verified status in this repo (2026-11-16): YOLO wrapper `src/lib/server/yolo.ts`, COCO-17 pose schema `src/lib/shared/pose-skeleton-schema-v1.ts`, source-bound annotation revisions `src/lib/server/features/evidence/evidence-revision-v1.ts`, `DepthReliefViewer.svelte`, `VideoAnalysisView.svelte` all exist. Missing: the CPU sampler (`workers/sample_10s.py` is not in the repo), any tracker (no ByteTrack), any pose or depth or segmentation model (no MediaPipe/RTMPose), blockout and mannequin code, and every `video_reconstruction_*` table (none in `legal_ai_db`, checked 2026-11-16).

- [ ] VR-00 Source identity gate: verify the existing evidence ID, immutable `sourceRevision`, source SHA-256, video stream, and timestamps before any work starts. Reuse `evidence` columns (`hash`, `file_url`, `video_codec`, `duration_seconds`, `frame_count`). Record fps from the decoder (see SCENE-26).
- [ ] VR-01 Frame sampling: decode on CPU with FFmpeg; reuse existing keyframe and motion-tile outputs where available. The pilot plan samples analysis at 2 FPS (about 20 frames) and motion at a separate rate. The sampler must be a repo file with tests, not the external draft.
- [ ] VR-02 Person detection and 2D pose: YOLO for boxes (existing). Pose model not yet admitted (see DEC-D). Output must keep the crop/letterbox transform and map keypoints back to source-frame pixels before storage.
- [ ] VR-03 Tracking: one stable track ID per person across frames. No tracker exists; ByteTrack or an equivalent is proposed, unadmitted.
- [ ] VR-04 Depth and segmentation: relative depth and person masks at about 2 FPS. Mark depth as `relative_monocular` (SCENE-03); do not treat it as metric.
- [ ] VR-05 Motion analysis: displacement, joint angles, velocity, and visibility per track, with uncertainty kept per sample.
- [ ] VR-06 Blockout and mannequin: a room blockout from the primitive registry (SCENE-20) and a simple rigged mannequin placeholder. Coordinates keep uncertainty and stay unscaled until calibrated (SCENE-12). Pose landmarks become room coordinates only after calibration.
- [ ] VR-07 Proposed GLB and scene manifest: write a GLB proposal and a manifest that cites the source revision, sampler and model revisions, and per-sample PTS. Inspect in the existing Three.js review viewer (see DEC-C).
- [ ] VR-08 Investigator review gate: nothing moves into the scene-revision authority without an explicit reviewer action. Reuse the source-bound annotation revision contract; a client may not assert `REVIEWED`.
- [ ] VR-09 Database: the draft adds five new tables (`video_reconstruction_runs`, `_tracks`, `_samples`, `_artifact_links`, `_scene_proposals`). Rules: draft and rehearse in the scratch database only, with `drizzle/manual` and a `proposal_only` sidecar entry (as for `20261116_evidence_pose_observations_v1.sql`). Do not recreate evidence, frame, analysis-job, or scene-revision tables. Apply only after a live-catalog reconciliation passes.
