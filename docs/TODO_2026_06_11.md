## Critical Architectural Adjustment: strategy_distribution Field

### Current Schema (3E as implemented)
```typescript
conceptTemperature: doublePrecision('concept_temperature').default(0.5),
```

### Recommended Addition
Add one more field to `concept_records`:

```typescript
strategyDistribution: jsonb('strategy_distribution').$type<{
  fusion?: number;
  vector_only?: number;
  lexical_only?: number;
  structural_only?: number;
  cold_neschrom?: number;
}>().notNull().default(sql`'{}'::jsonb`),
```

### Why This Matters

**Temperature alone answers**: "How hot is this concept?"  
**Distribution answers**: "WHY is this concept hot?"

#### Example
```json
{
  "concept_id": "authentication",
  "concept_temperature": 0.95,
  "strategy_distribution": {
    "fusion": 842,
    "vector_only": 131,
    "lexical_only": 62,
    "structural_only": 27,
    "cold_neschrom": 9
  }
}
```

**Without distribution**, you ask: "Is auth hot?"  
**With distribution**, you ask: "Why is auth hot? Because fusion found it 842 times, but we also found it via lexical (62) and vector (131)—it's robustly discoverable."

### Causality Preservation

This is critical for **Phase 3F+ learning**:
- "Concept A is hot because fusion keeps finding it" (reliable, multi-signal)
- "Concept B is hot because only vector search finds it" (brittle, single-signal)
- "Concept C is hot but discovered via cold_neschrom 9 times" (niche, rare path)

These are **different lessons for Gemma4 planner training**.

### Implementation

Update migration file:

```sql
-- Add strategy_distribution to concept_records
ALTER TABLE concept_records
ADD COLUMN IF NOT EXISTS strategy_distribution jsonb 
DEFAULT '{}'::jsonb NOT NULL;

CREATE INDEX IF NOT EXISTS idx_concept_records_strategy_dist_gin
ON concept_records USING GIN(strategy_distribution);
```

Update Drizzle schema:

```typescript
export const conceptRecords = pgTable('concept_records', {
  // ... existing fields ...
  conceptTemperature: doublePrecision('concept_temperature').default(0.5),
  strategyDistribution: jsonb('strategy_distribution').$type<Record<string, number>>().notNull().default(sql`'{}'::jsonb`),
  // ... timestamps ...
});
```

## Important: Delay agent_traces

### Current Temptation
```
retrieval_telemetry
  ↓
agent_traces (immediately)
```

### Recommended Flow
```
retrieval_telemetry (factual: what happened)
  ↓
concept_records (aggregated: what patterns exist)
  ↓
agent_traces (interpreted: what did agents decide)
```

### Why
- **Telemetry is factual** — Query → Retrieval → Hits
- **Concepts are synthetic** — Evidence aggregated, temperature computed
- **Traces are interpretative** — Repair outcome + success judgment

**Problem with early traces**: Agent traces without concept context are orphaned data.  
**Solution**: Let concept memory stabilize first (1–2 weeks of live telemetry), then layer agent traces on top with full concept context.

### Timeline
- **Week 1–2**: Telemetry → Concepts pipeline (Phase 3E.1)
- **Week 2–3**: Agent traces (Phase 3F, once concepts are stable)
- **Week 3–4**: QLoRA export (concepts + traces → training examples)

## Neo4j Graph: Add Two Edge Types

### Current Graph Shape
```
SourceRef
  ↓
Feature
  ↓
Packet
  ↓
Concept
```

### Add Two Relationship Types

#### 1. Concept ──DISCOVERED_BY──→ RetrievalStrategy
```cypher
MATCH (c:Concept {id: $concept_id})
CREATE (c)-[:DISCOVERED_BY {count: 842, strategy: 'fusion'}]->(rs:RetrievalStrategy {name: 'fusion'})
```

**Use**: "Find concepts discovered primarily via fusion (high-quality discovery)."

#### 2. Concept ──UPDATED_BY──→ TelemetryEvent
```cypher
MATCH (c:Concept), (te:TelemetryEvent {id: $event_id})
CREATE (c)-[:UPDATED_BY {timestamp: now(), strategy: 'fusion', success: true}]->(te)
```

**Use**: "Trace the retrieval history of a concept; see exactly which events contributed to its temperature."

### GDS Query: Concept Value Pipeline

```cypher
-- Which retrieval paths create the highest-value concepts?
MATCH (c:Concept)-[:DISCOVERED_BY {strategy: 'fusion'}]->()
WHERE c.concept_temperature > 0.8
MATCH (c)<-[:REFERENCES]-(f:Feature)
RETURN c, count(f) as feature_importance, c.concept_temperature
ORDER BY feature_importance DESC
```

**Use**: For Gemma4 planner training — "Learn which retrieval strategies lead to valuable concepts."

## QLoRA Dataset Shape (Final Form)

### NOT This
```json
{
  "prompt": "fix auth bug",
  "completion": "added isAuthenticated guard"
}
```

### NOT This Either
```json
{
  "code_before": "...",
  "code_after": "..."
}
```

### BUT THIS
```json
{
  "query": "fix missing auth guard in POST /api/cases",
  "retrieval_strategy": "fusion",
  "selected_concepts": [
    "auth_guard_pattern",
    "api_endpoint_validation",
    "error_handling_boilerplate"
  ],
  "selected_packets": [
    "packet_001_auth_guard",
    "packet_003_validation_pattern"
  ],
  "repair_outcome": "success",
  "reward": 0.94,
  "repair_diff_stats": {
    "files_touched": 1,
    "lines_added": 5,
    "lines_deleted": 0,
    "tests_passing": 5,
    "tests_failing": 0
  }
}
```

### Why This Shape Teaches Gemma4 Planner

Current model learns:
```
Problem → Answer
```

New model learns:
```
Problem
  ↓
Retrieval Lane Choice (fusion? vector?)
  ↓
Concept Selection (which 3 concepts matter?)
  ↓
Repair Outcome (success? reward 0.94?)
```

**This is agentic planning**, not text generation. Gemma4 learns:
- "For auth bugs, use fusion strategy"
- "For auth bugs, retrieve auth_guard_pattern + error_handling"
- "Reward: 0.94 when all tests pass"

## Questions for Architecture Review

1. **strategy_distribution cardinality**: Should it count *occurrences* (how many times this concept was found via fusion) or *proportion* (85% fusion, 12% vector, 3% lexical)? *Recommended: count occurrences* (raw signal, easier to aggregate).

2. **Trigger vs Job**: Concept updates on every telemetry record (could be high volume). Use:
   - **Trigger** if telemetry is low volume (<1k/hr)
   - **Batch job** if telemetry is high volume (>1k/hr)
   - *Recommended: Batch job* (safer, easier to observe)

3. **Temperature decay**: When last_retrieved_at is old, temperature decays. How aggressively?
   - *Current formula*: 0.50·recent + 0.30·success + 0.20·fusion
   - *Alternative*: Add time decay factor (0.95^days_since_retrieval)
   - *Decision*: Keep formula simple; decay via recency window in SQL.

4. **Agent traces timing**: Start Phase 3F after Phase 3E.1 has >500 records with meaningful strategy_distribution? *Yes.*
