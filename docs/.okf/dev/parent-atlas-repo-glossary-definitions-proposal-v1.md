# Parent Atlas Repository Glossary Definitions — Proposal v1

**Status:** REVIEW_ONLY  
**Authority:** Non-canonical documentation proposal; not an OBO edit, corpus admission, or runtime configuration.  
**Purpose:** Give high-frequency repository terms a lexical definition, a Parent Atlas-specific meaning, and the current code owner(s) to inspect.

The codebase notes below describe the inspected source contracts. They do not claim that an optional service, model, native binary, or GPU backend is currently live. A source path is a navigation pointer; a citation or admission decision still requires current revision and byte verification.

## Deliberate distinctions and review notes

- Keep `sourceRevision`, `workspaceRevision`, `representationRevision`, and `featureRevision` as separate terms. Do not add an undifferentiated **revision** concept that merges their identity scopes.
- Keep `semantic_768` as a representation name, not an ontology domain. Keep product/platform terms such as Redis, Qdrant, pgvector, Valkey, and EmbeddingGemma in a technology vocabulary or an explicitly reviewed platform branch; do not silently place them under software domains or programming languages.
- The existing OBO file already contains a CUDA platform concept. This draft does not mint new OBO IDs or assert that all listed products belong in that ontology.
- The existing `.okf/corpora/keyword-corpus.yaml` groups terms for lexical discovery. It is not a term-by-term lexical/semantic/codebase glossary and its frequency counts are not evidence of concept validity.
- Before promoting any definition into the keyword corpus or OBO, review product naming, aliases, taxonomy parent, source pointers, and term-sense ambiguity. In particular, **Redis** can refer to the protocol-compatible ecosystem or a particular product, and **Graphify** is a repository label rather than a universal technical standard.

## Proposed disposition

Use this file as the review sheet. After human review, copy only accepted lexical aliases and repository-specific definitions into the existing keyword-corpus owner. Create OBO terms only for concepts with an approved taxonomy parent and stable identifiers. No data-store, ontology, or classifier changes are authorized by this proposal.
