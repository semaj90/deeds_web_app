# DB Schema Migration Guidelines — Parent Atlas

Date: 2026-05-30

Purpose
-------
Capture operator-led decisions and safe procedures for Drizzle-generated migrations, identity strategy for `users.id` / `user_id`, and handling manual SQL sidecars.

1) Identity strategy (operator MUST decide)
-----------------------------------------
Do not proceed with mass migrations until the operator chooses one option. Each has tradeoffs:

- Path A — All integers
  - `users.id` = serial/integer; all `user_id` columns integer FKs.
  - Pros: Referential integrity, smallest storage, fastest joins.
  - Cons: Requires migrating historical uuid/text IDs; breaks services expecting string IDs.

- Path B — All UUIDs
  - `users.id` = uuid; all `user_id` = uuid.
  - Pros: Globally unique, easier cross-system merger.
  - Cons: Requires migrating integer PKs and code changes; may break Lucia/other auth assumptions.

- Path C — Two-tier (`users.id` INT + `users.uuid` UUID)
  - `users.id` remains integer PK; `users.uuid` added as canonical external id.
  - `user_id` consumer columns can choose to reference either `id` (int) or `uuid` (uuid).
  - Pros: Highest compatibility; preserves DB joins and external references.
  - Cons: Extra column and join complexity; requires disciplined application changes.

- Path D — Defer / Coerce forever
  - Leave mixed types; always coerce at read/write boundaries (application-level mapping).
  - Pros: Low migration effort.
  - Cons: Technical debt, potential for hard-to-find bugs, degraded integrity.

Operator MUST confirm which Path to adopt before any automated conversions.

2) Drizzle migration safety rules
--------------------------------
- Always eyeball every `CREATE/ALTER/DROP` generated by `drizzle-kit generate` before applying.
- `drizzle-kit generate --name=foo` writes `drizzle/0NNN_foo.sql` and updates `drizzle/meta/_journal.json`.
  - To inspect without journaling:
    1. Run `drizzle-kit generate --name=preview-foo`.
    2. Copy the generated SQL somewhere safe for review.
    3. Revert journal changes: `git checkout drizzle/meta/_journal.json` and then `rm drizzle/0NNN_preview-foo.sql`.
- Manual SQL sidecars live in `drizzle/manual/*.sql` and are NOT recorded in the journal. Any auto-generated migration that re-CREATEs those tables will collide — verify with `ls drizzle/manual/` and cross-check CREATE statements.

3) `tablesFilter` semantics
---------------------------
- `!table_name` patterns suppress `drizzle-kit generate` from emitting DROP TABLE statements for those tables.
- They DO NOT suppress CREATE TABLE for tables declared in `schema-postgres.ts` but missing from DB. To skip a CREATE, either remove the table from the schema file or manually delete the CREATE from the generated SQL before applying.

5) Schema mismatch: `user_id` fragmentation (how to detect)
---------------------------------------------------------
Run this SQL to list columns named `user_id` or `uploaded_by` and their types:

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE column_name IN ('user_id','uploaded_by') AND table_schema='public'
ORDER BY data_type, table_name;
```

Quick scanner (psql):

```bash
psql "$DATABASE_URL" -c "COPY (SELECT table_name, column_name, data_type FROM information_schema.columns WHERE column_name IN ('user_id','uploaded_by') AND table_schema='public' ORDER BY data_type, table_name) TO STDOUT WITH CSV"
```

6) Recommended conservative workflow (must follow)
--------------------------------------------------
- STOP before running any automated convert if identity strategy is undecided.
- Perform a non-destructive `drizzle-kit generate` and review SQL for:
  - Any `CREATE TABLE` that affects `user_id` columns.
  - Any `DROP TABLE` — ensure tables are not DB-only protected.
- Maintain a checklist per migration:
  - Operator-signed identity strategy
  - Review of `drizzle/0NNN_*.sql` by two engineers
  - Cross-check against `drizzle/manual/*`
  - Run `psql` inspection queries and attach CSV output to the migration PR
  - Run staging apply and smoke-tests (API + auth flows)
- Prefer Path C (two-tier) when in doubt — adds `users.uuid` and migrates external systems incrementally.

7) Handling manual sidecar migrations
------------------------------------
- Keep a manifest `drizzle/manual/_manifest.json` describing which tables were applied manually and why.
- Any generated migration that touches a manual table must be reconciled by hand: either remove the generated CREATE/ALTER or rebase manual SQL into the journal with a careful patch.

8) Quick remediation suggestions
--------------------------------
- If you choose Path C (recommended conservative):
  1. Add `users.uuid` UUID NOT NULL DEFAULT gen_random_uuid() to the `users` table.
  2. Backfill `users.uuid` for existing users (one-time script).
  3. For tables using `uuid` columns today, add an integer `user_id_int` FK column and populate by joining on `users.uuid` → `users.id`.
  4. Migrate application code to prefer `users.uuid` for external references, and `users.id` for internal joins.
- Avoid blind mass `ALTER TABLE` conversions until tested in staging.
