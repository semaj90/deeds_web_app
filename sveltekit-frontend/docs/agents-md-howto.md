# AGENTS.md — How-to Guide

> Per-directory LLM context wiki, indexed → reranked → compressed → retrieved through the Graphify pipeline. Reference for future agents (Claude Code, Cursor, OpenAI Codex, Hermes, Aider) and humans navigating the codebase.

---

## 1. What is AGENTS.md?

[AGENTS.md](https://agents.md) is a community-standard convention: a plain-Markdown file inside any source directory tells coding agents what that directory does, what conventions to follow, and what NOT to do. Every modern agent (Claude Code, Cursor, Codex, Hermes, Aider) walks **up** the directory tree from the file under work and injects the nearest `AGENTS.md` into its system prompt.

This repo has **three tiers** of AGENTS.md, all auto-generated from the GPU codebase indexing pipeline:

| Tier | File | Purpose | Source data |
|------|------|---------|-------------|
| 1 — Repo root | [`/AGENTS.md`](../../AGENTS.md) | Entry point + pointer index + repo-level conventions | Hand-curated + audit gate snapshot |
| 2 — Frontend wiki | [`sveltekit-frontend/AGENTS.md`](../AGENTS.md) | LLM directory wiki — every dir + cluster + KAG slug + tool call | All sources joined |
| 3 — Per-dir | `sveltekit-frontend/src/**/AGENTS.md` (~250 files) | Cluster topic, file list, KAG narrative, agentic tool examples | Per-dir join |

```bash

Or via VS Code task:

- **🤖 Graphify: AGENTS.md (dry-run preview)** (read-only)

The generator is at [`scripts/generate-agents-md.mjs`](../scripts/generate-agents-md.mjs).

### Pipeline integration

```
graphify:full
  ├── graphify:daily         # Fast AST → docs/graph/codebase-graph.json + Redis code:index:*

## 3. The 5-source join (what powers each AGENTS.md)

Each per-dir AGENTS.md is generated by joining 5 in-pipeline sources — **no LLM calls, no GPU at generation time**. Just typed aggregation over JSON + Redis.

| Source | Path | Provides | Cost |
|--------|------|----------|------|
| Fast AST graph | `docs/graph/codebase-graph.json` | per-file flags (auth, Zod, SSR, todos, isRoute) + dir aggregates | ~3-5s CPU |
| Hypergraph clusters | `docs/graph/hypergraph-clusters.json` | dominant cluster topic per dir + topKinds/topTags | ~30-60s GPU |
| KAG wiki notes | Redis `wiki:note:dir:dir:<slug>` | narrative purpose, summary, auditScore, neighbors, patterns | <100ms |
| Cluster digest | `docs/graph/hypergraph-clusters.md` | human-readable cluster topics | bundled with above |
| Codebase map | `docs/graph/codebase-map.md` | 20-gate audit dashboard | bundled |

### Per-dir AGENTS.md structure

```
# AGENTS.md — `src/lib/server/cache`

<!-- AGENTS-GEN v1 · do not edit below this line -->

## Snapshot
- Audit score: 90/100
- Tags: redis, vector, embedding

## Files (8)               ← from graph JSON dirFiles
- cache-events.ts
- redis-exact-match.ts
...

## Hypergraph cluster      ← from hypergraph-clusters.json (when matched)
This directory is part of cluster **C22** — function chunks in `src/lib/server/cache` (tag: redis)
- Top kinds: function×13
- Top tags: redis, vector, embedding, cache, rabbitmq

## Topological neighbors   ← from KAG (populated by GPU runs)
## Patterns / Warnings     ← from KAG
## PageRank Top-5          ← from KAG (GPU)

## Agentic tool-calling — quick ACE hits   ← context for LLM tool calls
- graph_search({ query: "cache", topK: 8 })
- wiki_note_lookup({ query: "server cache", limit: 5 })
- audit_hotspots({ limit: 10 })
- read_file({ filePath: "src/lib/server/cache/<file>" })
```

## 4. Idempotency — human edits are preserved

Every generated file carries a stable header marker:

```html
<!-- AGENTS-GEN v1 · do not edit below this line -->
```

On regen, the generator:
- **File has the marker** → overwrite (data refresh)
- **File lacks the marker** → assume human-edited, **preserve as-is**, log `⏸ preserved`
- **File doesn't exist** → write fresh

To customize a directory's AGENTS.md permanently:

1. Run `npm run agents:write` to get the generated baseline
2. Delete the `<!-- AGENTS-GEN v1 -->` marker line
3. Edit freely — future regens won't touch it

Or add manual notes ABOVE the marker — those are also preserved (the marker only protects content below it).

## 5. Reranking against `next_steps/`

The `next_steps/active/` backlog contains structured fix plans (auth-gaps, directory-consolidation, production-blockers). The AGENTS.md system feeds these:

```
next_steps/active/2026-05-03-auth-gaps.md
  ↓ source: graph_search({ onlyNoAuth: true, topK: 30 })
  ↓ + wiki_note_lookup for narrative context per dir
  ↓ + agents_md({ path }) for tool-call examples per dir
  ↓
agentic-batch-fix.mjs runs Gemma4 in parallel on top hotspots
  ↓ each task gets the right per-dir AGENTS.md auto-loaded
  ↓
fix plans written to next_steps/active/{date}/batch-fix-{ts}/
```

### Rerank workflow

1. **Refresh signal**: `npm run graphify:daily` (recomputes audit scores)
2. **Find hotspots**: `npm run audit:dirs:summary` (1-line summary per dir)
3. **Update backlog**: edit `next_steps/active/2026-05-03-auth-gaps.md` to drop fixed items, add new ones from the refreshed `codebase-map.md` Directory Scorecard
4. **Drive fixes**: `npm run agent:fix:batch:summary -- 5` — top 5 hotspots → Gemma4 parallel agent loops → per-dir fix plans

The `next_steps/` reranking is currently **manual review** (you read the new map, prune stale items, add new). A future `audit:rerank-next-steps` script could automate the diff — see [§9 Future ideas].

## 6. Bifrost / Redis L1+L2 cache integration

The **3-tier cache** in front of Ollama works orthogonally to the AGENTS.md system but they share Redis:

```
User query / agent prompt
  ├─ L1: Redis exact-match cache       (5ms, key = SHA-256 of model+messages+temp)
  │   └─ src/lib/server/cache/redis-exact-match.ts
  │
  ├─ L2: Bifrost semantic cache        (2-5s, vector similarity ≥0.8)
  │   └─ Port 3040 (go-microservice/cmd/bifrost/)
  │
  └─ L3: Direct Ollama GPU             (25s, cold inference)

Combined hit rate: 90-95% → 90% cost reduction
```

### Where AGENTS.md content fits in caching

**Per-dir AGENTS.md is itself cacheable** — when an agent calls `agents_md({ path })`, the result is:
1. Read from disk (fast, OS page cache hits)
2. Mirrored to Redis `agents:dir:<slug>` (24h TTL) at write time
3. Fetched from Redis on subsequent in-process tool calls (avoids fs.readFile overhead)

The `agents:write` script automatically does steps 1-2 in a single pass:

```bash
$ npm run agents:write
✓ wrote 247 AGENTS.md file(s), mirrored to Redis agents:dir:* (247 keys, 24h TTL)
```

### Cache invalidation on regen

When `npm run agents:write` rewrites a file:
- Disk file: replaced atomically
- Redis `agents:dir:<slug>`: SET overwrites old key (24h TTL refresh)
- Bifrost L2 cache: NOT invalidated (cache keys are LLM-prompt SHA, not AGENTS.md SHA)

If you want agent loops to see the freshest AGENTS.md immediately:

```bash
# Invalidate L1 keys that mention a directory you just regenerated
docker exec legal-ai-redis redis-cli --scan --pattern 'l1:*' | grep '<dir>' | xargs docker exec -i legal-ai-redis redis-cli del
```

In practice, the L1 hit rate drops naturally as new prompts come in, so manual invalidation is rarely needed.

## 7. Qdrant tag-cluster compression for indexed retrieval

The hypergraph topology stage tags every Qdrant point in `codebase_chunks_768` with its cluster id:

```
Qdrant payload
{
  "path": "src/lib/server/cache/redis-exact-match.ts",
  "kind": "function",
  "tags": ["redis", "cache", "exact-match"],
  "som_cluster": 22,            ← from hypergraph:tag step
  "som_bmu_row": 3,
  "som_bmu_col": 7,
  "content_hash": "..."
}
```

This enables **filter-then-search** queries that compress the search space ~100× before doing the expensive vector ANN:

```typescript
// Naive: search all 32,753 vectors
const all = await qdrant.search({
  collection: 'codebase_chunks_768',
  vector: queryEmbedding,
  limit: 10,
});

// Tag-clustered (the AGENTS.md path): pre-filter to ~300 vectors in cluster 22
const tagged = await qdrant.search({
  collection: 'codebase_chunks_768',
  vector: queryEmbedding,
  limit: 10,
  filter: {
    must: [{ key: 'som_cluster', match: { value: 22 } }],
  },
});
```

The cluster id comes from the directory's AGENTS.md (the `Hypergraph cluster` section). When an agent reads a dir's AGENTS.md and sees "Cluster C22", it can then issue cluster-filtered Qdrant queries that are:

- **~100× faster** (search 300 vectors vs 32k)
- **More relevant** (results stay in the same semantic neighborhood)
- **Cheaper to rerank** (smaller candidate set)

### How clusters are formed

```
Stage 3 (hypergraph:export):
  Qdrant scroll → 32,753 × 768-dim NDJSON

Stage 4 (hypergraph:build:redis):
  K=100 streaming k-means (no GPU) → centroids.json + assignments.ndjson + Redis hg checkpoints

Stage 5 (hypergraph:tag):
  For each (point_id, cluster_id) in assignments → SET payload som_cluster on Qdrant point

Stage 6 (hypergraph:digest):
  For each cluster → join member payloads → emit hypergraph-clusters.{md,json}
```

The digest's `inferredTopic` field ("function chunks in `src/lib/server/cache` (tag: redis)") is what lands in each per-dir AGENTS.md.

## 8. TypeScript-style "minified" codebase mapping

The end-to-end pipeline acts as a multi-stage **lossy compression** over the codebase. Each stage drops detail you don't need at that level:

| Stage | Input size | Output | Compression ratio | Detail kept |
|-------|-----------|--------|-------------------|-------------|
| 0. Source | ~80 MB across 2,581 files | — | 1× | Everything |
| 1. Fast AST | 80 MB | `codebase-graph.json` (2.7 MB) | 30× | per-file flags, imports, exports, tags |
| 2. Codebase map | 2.7 MB JSON | `codebase-map.md` (52 KB) | 50× | gate dashboard, scorecard, top issues |
| 3. Per-dir KAG | 80 MB | Redis `wiki:note:dir:*` (~1.5 MB total) | 50× | narrative purpose per dir |
| 4. Qdrant 768d | 80 MB | 32,753 × 768 floats (~100 MB) | 0.8× | semantic distance lookups |
| 5. Hypergraph K=100 | 100 MB | `hypergraph-centroids.json` (2 MB) | 50× | 100 cluster centroids + counts |
| 6. Cluster digest | 100 MB | `hypergraph-clusters.md` (72 KB) | 1400× | 100 topic labels |
| 7. AGENTS.md (per-dir) | 80 MB | ~250 files × 2-3 KB = 600 KB | 130× | dir-scoped LLM context |
| 8. Frontend wiki | 80 MB | `sveltekit-frontend/AGENTS.md` (40 KB) | 2000× | 1015-row directory index |

The **frontend wiki at 2000× compression** is the smallest representation — that's what an agent should load first when navigating an unfamiliar repo.

### Why this matters for LLM context windows

A 200K-token window can fit:
- ~10 source files at 80 KB each, OR
- ~50 KAG notes, OR
- **The entire frontend wiki + 30 per-dir AGENTS.md + 8 source files** — full repo navigation context with budget left for the actual task

The compression isn't lossy in a useful sense — each tier preserves what the previous tier's *consumer* needs:

- **Humans navigating** → frontend wiki (`sveltekit-frontend/AGENTS.md`)
- **LLM editing a file** → per-dir AGENTS.md (auto-loaded by walking up)
- **LLM doing audit** → `codebase-map.md` (gate counts + scorecard)
- **LLM doing semantic search** → Qdrant + cluster filter
- **LLM exploring related code** → cluster digest (`hypergraph-clusters.md`)

### TypeScript reranker pattern

When building tools that consume the wiki (e.g. `agents_md` Gemma4 tool), the rerank pattern is:

```typescript
// 1. Coarse filter — directory tree map (fastest)
const dirHits = parseFrontendAgentsMd().filter(d => d.tags.includes(query));

// 2. Mid-rerank — per-dir cluster topics (load just the matched dirs)
const reranked = dirHits.sort((a, b) => {
  const aRel = clusterRelevance(a.cluster, query);
  const bRel = clusterRelevance(b.cluster, query);
  return bRel - aRel;
});

// 3. Fine — Qdrant cluster-filtered semantic search on top-3
const finalResults = await Promise.all(
  reranked.slice(0, 3).map(d => qdrant.search({
    filter: { must: [{ key: 'som_cluster', match: { value: d.clusterId } }] },
    vector: queryEmbedding,
    limit: 5,
  }))
);
```

This is the same coarse-to-fine cascade as in `src/lib/server/ace/context-assembler.ts` (priority order):

```
1. Qdrant codebase_chunks_768       (semantic, highest signal)
2. ACP knowledge cross-feed         (semantic)
3. Redis wiki:note:dir:* KAG        (narrative, cap 0.08)
4. Redis code:index:* fast-AST      (lexical, cap 0.07)
5. SOM/hypergraph/PageRank          (topology, when GPU index exists)
```

Each tier is roughly 10× cheaper than the next but covers ~10× narrower context. The cascade short-circuits as soon as enough relevance is hit.
